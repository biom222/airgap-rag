# Эксперименты с квантизацией

Проект не реализует собственный quantizer. Квантизацию выполняет проверенный
model runtime или внешний toolchain, а AirGapRAG только измеряет готовые локальные
артефакты.

## Начальная матрица

| Вариант | Runtime/формат | Ожидаемый компромисс | Статус |
|---|---|---|---|
| FP16 | runtime с FP16 weights | базовая точность, максимальная память | не измерен |
| GGUF Q8 | Ollama/llama.cpp | близко к FP16, меньше память | не измерен |
| GGUF Q4_K_M | Ollama/llama.cpp | существенно меньше память, возможна потеря качества | не измерен |
| AWQ | совместимый runtime | GPU-oriented 4-bit | следующий этап |
| GPTQ | совместимый runtime | GPU-oriented post-training quantization | следующий этап |

Статусы намеренно не содержат чисел до реального запуска на целевом
оборудовании.

## Что фиксировать

Для каждого артефакта используются одинаковые prompt и generation settings.
Нужно записать:

- точное имя и checksum модели;
- runtime и его версию;
- quantization;
- размер модели;
- RAM и VRAM;
- TTFT, tokens/sec и total latency;
- input/output tokens;
- retrieval quality dataset и метрики качества ответа.

Latency без quality недостаточна: более быстрая модель, которая теряет важные
факты или citations, не является автоматическим улучшением. Для retrieval
используется evaluation из `docs/evaluation.md`; качество generation требует
отдельного версионируемого набора вопросов и эталонных критериев.

## Процедура

1. Подготовить все варианты модели офлайн и проверить checksum.
2. Последовательно загрузить один вариант, не меняя prompt и параметры.
3. Выполнить одинаковый warm-up и число измеряемых итераций.
4. Запустить `python -m benchmarks.llm` с точной меткой `--quantization`.
5. Сохранить JSON и при необходимости строки PostgreSQL.
6. Сопоставить performance с quality evaluation.

Нельзя переносить метку quantization из имени файла без проверки metadata:
ошибочная метка делает сравнение недостоверным.
